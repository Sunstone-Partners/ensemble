## 4. Deviations from the plan or TRD

1. **The ambiguity fixture seeds two lookalike beads, not one.** The plan's wording ("a second bead
   with the same task marker") was realised by seeding **two** `[trd:widget-engine:task:TRD-002]`
   beads (`dup-1`, `dup-2`) before the scaffold. With a single seeded duplicate the scaffold's own
   title-prefix cache reuses it and only one bead carries the marker, so the test saw exit 0; that
   is the red run recorded above for that scenario and the fixture was corrected, not the code.
2. **`FOREMAN.tagged` is 8, not 9, on the 12-bead fixture.** The plan's E20 sketch says "task
   count"; the fixture's task-level beads are 8 (4 tasks + 4 tests; the synth bead is one of the
   12 only when `synth` is on, and the hierarchy here is 1 epic + 2 stories + 8 task-level + 1
   synth). The assertion pins the number the fixture actually holds and the per-bead check proves
   epic and story beads are never tagged.
3. **`outputSchema.required` narrowed.** The plan says the health keys stay out of `required`; in
   practice that means `required` becomes `['MODE','TRD_FILE_PATH','TRD_SLUG','WARNINGS']`, because
   `reset-task` answers with no health keys at all. The per-key schemas are unchanged and
   `additionalProperties:false` still holds.

Nothing else deviates. Every escalation default in PLAN.md section 5 was adopted as written; no
other contradiction was decided here.

## 6. Escalations and follow-ups

For the PR body (E26), prominently:

1. `implement scaffold` and `implement bead-health` are both registered `sideEffect: 'write'`.
   `bead-health` writes **only** behind `--label`, `--foreman` or `--reset-task`; the claim
   "nothing is changed" holds only without those three flags, and the read-only scenario proves it
   by hashing the stub's state and its mutation log before and after.
2. **The edge diff cannot read live edges on the shipped `beads` and `kata` adapters.** No
   capability lists edges and neither adapter's `tracker.show` mapping carries `dependencies`, so
   on them `bead-health` reports `EDGES.checked:false` with a warning. Edge-drift detection is
   proven only against the test stub until those adapters expose `dependencies`. The PR must not
   describe `bead-health` as working edge-drift detection on real trackers (plan escalation 3 —
   operator decision: map `dependencies` in those two manifests, outside this PR).
3. `--label` goes through `trd-cli beads-label`, which runs `tracker.label` **in-process and
   ungated** (no preflight, confirmation or ledger — `beads-label.js:25-37`). The TRD asks for
   exactly that (TRD:416). Plan escalation 5; default adopted.
4. Neither TRD-011 nor TRD-012 is listed security-sensitive in the TRD (TRD:701 names only TRD-001
   and TRD-016), and TRD-012 adds no input boundary, so this PR is not flagged for a security
   reviewer — but it does write to the tracker through the existing gated capabilities
   (`tracker.label`, `tracker.set-status`, `tracker.sync`), plus the ungated path of item 3.
5. Confirmation is not called by the verb (plan escalation 4): on an unconfirmed adapter an
   interactive run is refused by the toolchain's own `CONFIRMATION_REQUIRED`, and a run without
   `--run-id` by `PREFLIGHT_REQUIRED`. The caller confirms first or passes `--non-interactive`.
6. Authored message texts (`labelFailed`, `foremanTaggingFailed`, `foremanTaggingIncomplete`'s
   count suffix, `resetTaskFailed`) await wording review (plan escalation 9); a rewording changes
   one constant in `messages.js`.
7. `--describe` goes from 43 to 45 verbs across PR 3 (7 in `implement`).

Intentionally left undone, per the plan's "Out of scope": the skill and command prose, the
toolchain command manifest (escalation 15), `docs/guides/ensemble-engine.md`, the changelog and
versions, and anything from TRD-013 onwards.
