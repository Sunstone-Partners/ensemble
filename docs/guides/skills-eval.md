# Skills eval: arms, repeats and the Claude Code and Pi adapters

How `node evals/run.js --skill <skill> --runtime claude` measures a skill: each eval runs with the skill and without it, repeated, and reports reliability, uplift and whether the skill was actually invoked. General harness usage is in `evals/README.md`; this guide records how the Claude Code and Pi adapters load and detect skills and what the numbers mean.

## Arms

| | with-skill | baseline |
|---|---|---|
| Workspace | fresh copy of `fixture/` | identical fresh copy |
| Prompt | `prompt` (`explicit`: `command` + space + `prompt`; `explicit-both`: the same in both arms) | `prompt` (with `explicit-both`: `command` + space + `prompt`) |
| Settings | `--setting-sources project`, same tools, turns, model | the same |
| Loaded | `--plugin-dir packages/<pkg>`: the package that ships the skill, as shipped (never a copy), after any `sharedPackages` | no plugin for the skill under test (only the eval's `sharedPackages`, when it names any) |

`--setting-sources project` is passed to both arms, so user-level settings and synced or marketplace plugins cannot leak into either one. The job passed to the runner carries `pluginDirs[]` (a list: a skill may need more than one package) and `skillPaths[]`. An eval whose command lives in another package than its skill names that package in `sharedPackages`: both arms load it, the with-skill arm adds the skill's own package. It must not be the skill's own package, the eval must be Claude-only (`runtimes: ["claude"]`), and `invocation: "explicit-both"` puts the command in front of the prompt in both arms so the baseline runs the same command without the skill.

A baseline run is checked for isolation. Missing evidence is never read as clean:

- **Leak.** The eval aborts, naming the leak, when the runtime reports the skill under test as loaded, the transcript invokes it, or its package appears among the loaded plugins (plugin paths are compared by `realpath` on both sides, falling back to the resolved path when it does not exist, so a symlinked path is still caught). A leak outranks the cases below.
- **`baseline isolation unverifiable: no startup skill list`.** A baseline that completed normally (not timed out, exit 0) whose stream had no `system`/`init` skills list (`loadedSource` is not `startup-event`) cannot be told from a leaked one. The eval aborts under that name, exactly like a leak.
- **Crashed or timed-out baseline before any init event.** That run is marked `outcome: "unverifiable"` and is not counted toward the baseline score (it appears as `notRun` and in `baseline.unverifiable`; its cost still counts). The eval continues with the remaining runs.

After an abort the baseline is not scored (`baseline: null`, no uplift), runs of that eval that have not yet started are skipped, and the run exits 1. A skill the model already knows is not a leak: its baseline passes too and the uplift is near zero, which is a valid result.

Several `system`/`init` events in one stream are unioned (skills and plugins); a later event never overwrites an earlier one.

**Fixtures.** The workspace is a copy of `fixture/`, and both arms use `--setting-sources project`, so project configuration in the fixture would be honoured and run with the agent's environment. An eval whose fixture contains `.claude/`, `.claude.json`, `.mcp.json`, `.git`, `.gitmodules`, `.gitattributes` or `.gitconfig` (at any depth, any letter case), or a symlink that points outside the fixture (or has an absolute target), is rejected with an error naming the eval and the file. The sandbox copy applies the same rules defensively: those entries are skipped, and a symlink is never followed out of the fixture.

**Judged checks** run on the with-skill arm only: `judgedScore` reads only that arm, so the baseline arm skips them and no judge spend is wasted (the judge reservation is not taken for baseline runs either).

**Definition limits.** `skill` must match `^[A-Za-z0-9._-]+$` (and not be `.` or `..`), and its directory must resolve under `packages/<pkg>/skills`. A `prompt` (or `command`) must not begin with `-`, and `allowedTools` entries must not contain a comma, a control character or leading/trailing whitespace (they are joined with commas on the command line; scoped patterns such as `Bash(git status:*)` are valid). A `bar` above `repeats` is rejected at load only when the eval sets both; otherwise it is checked at run time against `--repeats` or the `evals/limits.json` default.

## Repeats and reliability

Each arm runs `repeats` times (default 5, `evals/limits.json`), at most `--concurrency` at a time (default 4), with budget reserved per in-flight run (at most `--concurrency` runs are reserved at once). With-skill reliability is `passes >= bar` (default bar 4 of 5, `evals/limits.json`). The eval is `pass` when reliable, `fail` when the bar can no longer be reached, `incomplete` when the budget stopped it earlier.

- `repeats` and `bar` in `eval.json` override the defaults; `--repeats N` overrides both the eval and the default.
- When the bar is not set by the eval and the repeat count differs from the default, the default bar is scaled (`ceil(4/5 * repeats)`: 2 of 2, 3 of 3, 8 of 10). The report states each value and its source (`default`, `eval`, `flag`, `scaled`).
- A bar above the repeat count (an eval `bar` with a smaller `--repeats`) is a usage error, exit 2.
- `expectInvoked` is report-only: `invokedAsExpected` is recorded and printed, and the verdict does not change.

## Uplift

Uplift is the with-skill pass rate minus the baseline pass rate (a fraction, `+0.60` is 60 points). **For the Claude runtime it is package-level (skills share a package).** When an eval has `sharedPackages` the label names what the with-skill arm adds: `package-level (with-skill adds <packages>)`, in the live report and in a committed baseline (`withSkillAdds`). `--plugin-dir` loads a whole package, so every skill, command and agent in it is present in the with-skill arm, not only the skill under test. Pi loads one skill with `--skill`, so Pi uplift is skill-level. The two are not comparable quantities; the report prints the granularity beside the number.

## Claude Code startup events (probed)

Probed with Claude Code 2.1.311 (`claude -p ... --output-format stream-json --verbose --setting-sources project --model haiku --max-turns 1`), one run with `--plugin-dir packages/development` and one without, then one run asked to use a skill. Cost per probe run: about $0.002 to $0.004.

**The startup event does list loaded skills.** The first stream line is `{"type":"system","subtype":"init", ...}` with, among other keys:

- `skills`: array of skill names, plugin skills namespaced `<plugin>:<skill>` (for example `ensemble-development:completion-verification`), built-in ones bare (`verify`, `design`). 55 entries with the plugin, 19 without. It lists skills that are available, not skills that were used.
- `plugins`: array of `{ name, path, source, version }`. The loaded plugin appears with its absolute `path` (`.../packages/development`, `source` `...@inline`); built-in plugins have `path: "builtin"`. Without `--plugin-dir` only the four built-ins appear.
- Also `slash_commands`, `agents` (plugin ones namespaced), `tools`, `mcp_servers`, `model`, `claude_code_version`.

**Skill invocation event.** When the agent uses a skill, an assistant message carries a `tool_use` block `{"type":"tool_use","name":"Skill","input":{"skill":"ensemble-development:completion-verification"}}`, answered by a `tool_result` ("Launching skill: ...").

How the adapter uses this (`evals/lib/runners/claude.js`):

- `loadedSkills` is the union of the init event's `skills` and the skills named in `Skill` invocations; `invokedSkills` is the second set alone; `loadedPlugins` is the init `plugins` that have a path. `loadedSource` is `startup-event` when the init event carried a `skills` array, else `transcript-scan`. When the startup event lists no skills (another Claude Code version, a changed stream), `loadedSkills` is derived from the invocation events alone and the leak check uses that scan.
- The events are read as the stream arrives (not from the capped transcript), so a long run cannot push the init event out.
- A skill name matches `name` or `<plugin>:name`.
- `invoked` for a run is whether `invokedSkills` names the skill under test.

Observed, not controlled: the init event of every run listed claude.ai connector MCP servers (`mcp_servers`, 20 in the runs where the list was read; one early probe without a plugin listed none, which looks like connectors still loading). `--setting-sources project` does not remove account-level connectors, so they are present in both arms and do not differ between them, but they are not part of the skill under test.

Not verified: a slash command typed as the prompt (`invocation: explicit`) was not probed, so it is not known whether the stream shows it as a `Skill` tool_use. `invoked` counts only `Skill` tool_use events; an explicit-mode run that expands the command without that event would record `invoked: false`.

## Which copy was evaluated

Each eval result and the console state the evaluated copy: the package path loaded (`packages/<pkg>`), the skill directory's content hash (`skillHash`), the skill's `metadata.version` when present, and whether the working tree differs from the committed copy (`git status` on the package and on every `sharedPackages` package: each is loaded whole, so any edit in one counts, with the first changed files listed by repo-relative path, which names the package). `workingTreeDiffers` is `null`, shown as unknown, outside a git checkout. The installed (marketplace) copy is not inspected. For an eval with `sharedPackages` the package hash is one hash over the skill's package and each shared package (name and content hash, in order), so editing a shared package changes it, which invalidates cached results and makes committed baselines not like-for-like.

## Runner interface

`evals/lib/runners/index.js` registers runners by runtime name; `claude.js` and `pi.js` are registered (a runtime other than `claude` or `pi` is rejected with exit 2 and nothing runs). Each module also exports `RUNTIME`, `BIN_NAME`, `BIN_ENV` and `find()`. `run(job)` resolves `{ transcript, exitCode, timedOut, costUsd, loadedSkills, runtime }` plus `invokedSkills`, `loadedPlugins`, `loadedSource`, `stderr`, `transcriptTruncated`, `commands`, `commandsIncomplete`. A job is `{ evalId, skill, arm, runtime, model, prompt, workspace, env, timeoutMs, maxUsd, pluginDirs[] | skillPaths[], maxTurns, allowedTools }`. `costUsd` is `null` when the stream reported none, and the scheduler then charges the run's full reservation.

## Pi runtime

`node evals/run.js --skill <skill> --runtime pi [--model provider/id]` runs the same evals through headless Pi (`pi --print --mode json --no-session`, stdout is the JSON event stream; startup chatter such as hook and model-select notices goes to stderr). The binary is found on `PATH`, or via `EVALS_PI_BIN`. An eval runs under Pi only when its `runtimes` lists `pi` (default `["claude"]`); otherwise it is skipped with a `SKIP` line. If `--skill`/`--scenario` selected evals and the `runtimes` filter removes all of them, the run exits 2 naming the runtime and the evals; an unfiltered run that executes zero evals prints `0 evals ran under runtime <name>` and exits 4 (incomplete), never 0. A prompt beginning with `@` is rejected (Pi may read it as a file include), as one beginning with `-` is. Legacy single-arm scenarios are Claude-only. Judged checks still call the `claude` CLI (the judge is not a runtime), so `--runtime pi` with judged checks needs `claude` too; the judge model is compared to the model under test after stripping everything up to the last `/` (so `openrouter/anthropic/claude-sonnet-4` compares as `sonnet`) and a trailing `:thinking` suffix such as `:high`.

### Spike findings (TRD-012; Pi 1.5.2, run 2026-11-13)

1. **Loaded skills are readable from the output.** The system prompt travels in the message events and in `agent_end`; its skills section holds `<available_skills><skill><name>..</name><description>..</description><location>..</location></skill>...`. The harness reads the `<name>` values only from the system message's own `sections.skills` text and dedupes them, because the text repeats across events. For a parseable line it reads the `role: system` message of `message` / `messages`; for an `agent_end` line that is not valid JSON it takes the system object itself, found by brace depth with string and escape state, so nested arrays inside `sections` cannot end it early, and never reads beyond it. An `<available_skills>` block quoted in a later user message, tool result or assistant message of the same line is not counted. If no system message can be located the source is unverifiable (`loadedSource` stays `transcript-scan`, so the baseline check fails closed).
2. **`--skill <path>` alone does not isolate.** With only `--skill`, 145 unique skills were listed (the user-level `~/.pi/agent/skills` plus the one passed).
3. **`--no-skills` alone yields zero skills.** With it the system prompt has no skills section at all (its `sections` object lists preamble, tools, rules, docs, cwd and mcp_servers, not `skills`).
4. **`--no-skills --skill <dir>` loads exactly that one skill.** So the with-skill arm is `--no-skills --skill <skillDir>` and the baseline is `--no-skills`. A `--skill` path that does not exist loads nothing, silently; the adapter therefore refuses a skill path that is not an absolute directory holding `SKILL.md`.
5. **Cost is reported.** Assistant messages carry `usage.cost.total` (USD) next to `usage.{input,output,cacheRead,cacheWrite,totalTokens}`; streaming `message_update` events carry running or zero values. Per-message usage is per model call, so the adapter sums `usage.cost.total` over the assistant `message_end` events of a run. A model without prices reports `total: 0` (seen with a local router model); that is unknown, not free.
6. **Isolation flags.** Both arms also get `--no-context-files --no-extensions --no-mcp --no-approve --no-prompt-templates --no-themes --no-session --offline` (all probed together with `--no-skills --skill` and a real model call), and `--model` when one is given. The prompt is the final positional argument.

### How the adapter uses them

- **Arms.** Pi has no package-level loading, so the unit is the single skill: with-skill passes `--no-skills --skill packages/<pkg>/skills/<skill>` (the shipped directory, never a copy), baseline passes `--no-skills`. Pi uplift is therefore labelled **skill-level** (Claude stays "package-level (skills share a package)"); the two are not comparable.
- **Leak check.** The baseline's loaded-skills list must be empty (any skill, not only the one under test, since the baseline runs under `--no-skills`). The skills list is *readable* when the stream shows a system prompt (`loadedSource: system-prompt`): a system prompt without a skills block is then a verified empty list. If a baseline that completed normally (exit 0, no timeout) never showed a system prompt, the eval aborts as `baseline isolation unverifiable`; a baseline that crashed or timed out first is not counted. The invocation check also applies: a baseline that reads `<skill>/SKILL.md` or expands `/skill:<name>` is a leak.
- **Invocation.** A with-skill run counts as invoked when the stream shows a `/skill:<name>` expansion (a user message starting `<skill name="..." location=...>`) or a `read` tool call on `<name>/SKILL.md`. `invocation: explicit` prefixes `/skill:<name>` on the with-skill prompt under Pi (Claude's `command` is a package slash command, which Pi does not have).
- **Cost.** The reported sum is used when positive. Absent or zero cost, or a timed-out run, is unknown: the run is charged the per-run ceiling (`runReserveUsd` in `evals/limits.json`, `--run-usd`), flagged `costEstimated`, and counted against the suite cap like any other unknown cost. Pi has no budget flag, so the ceiling is accounting only; it does not stop a run (the timeout does).
- **Credentials.** Pi's provider keys are named under `runtimes.pi` in `evals/env-allowlist.json` (`OPENAI_API_KEY`, `GEMINI_API_KEY`, `OPENROUTER_API_KEY`); they reach Pi runs only. The judge is a separate `claude` process: it receives only the base credentials (`credentials` in the file) and any `--allow-env` names, never the runtime-scoped keys, and its output and stderr are redacted with every credential value (runtime keys included). Pi runs get the same throwaway empty per-run `HOME` that the checks get (probed with Pi 1.5.2: Pi still authenticates from a provider key in the environment with an empty `HOME`, whereas with the real `HOME` it may pick up its own login under `~/.pi/agent`). So under `--runtime pi` the provider key must come from the environment, and Pi's own auth files under the real `HOME` are not reachable.
- **Commands.** Any tool call in an assistant message whose arguments carry a string `command` is collected, whatever the tool is called (`execute_bash`, `powershell`, an extension tool), so forbidden-command checks work on Pi runs. The shell-like names (`bash`, `shell`, `sh`, `exec`, `terminal`, `run_command`, case-insensitive) only decide when a missing command means the list is incomplete; an unknown tool with a `cmd`, `script` or `commands` argument is flagged incomplete too. Any line mentioning `toolCall` is scanned whatever its key order or leading whitespace, and an unterminated final line is scanned too. The command list is flagged incomplete (so `noForbiddenCommand` fails closed) when such a line cannot be parsed (except `agent_end`, `message_update` and the other events that only repeat `message_end`), or a shell-like tool call has no string `command`.

### Known limits (Pi)

- **Hidden skills are not listed.** A skill with `disable-model-invocation: true` (for example `ensemble-create-prd`) is loaded by `--skill` but omitted from the system prompt's skills block, so `loadedSkills` does not show it. The with-skill arm does not require it to be listed, and the baseline cannot load it under `--no-skills`, but the leak check cannot see such a skill in the list; it can still see it invoked.
- **Tools and turns.** `allowedTools` (Claude tool names) and `maxTurns` are not passed to Pi (it has neither flag in the form used here), so Pi runs with its default tools; the arms still match each other. A Pi run of an eval that sets a non-empty `allowedTools` or a `maxTurns` prints one `WARNING` line per eval at start saying they are not applied.
- **Unverified.** The `/skill:<name>` expansion was probed with one skill and one model; a Pi `read` of `SKILL.md` was not seen end to end (the probe model did not use the tool as asked), so that invocation shape is taken from the tool-call schema in the stream.

## Results, baselines, report and coverage (PR 5)

**Versions.** `evals/lib/hash.js` computes `skillHash` (the skill directory) and `evalVersion` (`eval.json`, `rubric.md`, `fixture/`; a missing `rubric.md` is marked, not skipped). Entries are visited in codepoint order under POSIX paths, text files hash with LF line endings, no mtime or absolute path is hashed, the executable bit is, and `.DS_Store` is the only ignored name. A directory is hashed only through the files under it, so an empty directory contributes nothing and the hash matches a fresh git clone. A symlink is never followed: one inside the tree hashes as its relative target, one leaving it is an error; `eval.json` and `rubric.md` themselves must be regular files (a symlink or special file is a named error). `packageHash` hashes the whole `packages/<pkg>` directory by the same rules, because Claude loads the whole package while `skillHash` covers only `skills/<skill>/`. `skillVersion` is `metadata.version` from SKILL.md when present, else `null`.

**Records.** Every executed run becomes one record in the suite log (`records`), validated on write and on read (`results.readResult`, `results.readRecords`). A missing field is rejected with the file and field named; `skillVersion` and `judgeModel` may be `null` but the key must exist. Outcomes are `pass`, `fail`, `timed_out`, `incomplete`; the pipeline's internal `unverifiable` and `aborted` runs are stored as `incomplete` with `incompleteReason` and never count toward reliability. `replay` names the run (`evalId, skill, runtime, model, arm, run`) and carries the `command` that reruns it (see Replay below).

**Baselines.** `evals/baselines/<runtime>/<skill>.json` is small (counts, reliability, uplift, versions, `granularity`) and meant for committing; full logs stay in the gitignored `evals/results/` and the Evals workflow already uploads that directory as an artifact (no workflow change was needed). Only a finished eval is summarized (all planned runs executed and verified, no aborted baseline). Reading is strict: a file that is not valid JSON, lacks a field, has a `granularity` that contradicts its runtime, or sits at the wrong path is an error, never an empty baseline. The regression check `results.checkAgainstBaseline` compares a new result with the committed file; `evals/compare.js` does the like-for-like comparison of a suite log against the committed baselines (see Comparison below).

*Recorded model.* The `model` in a record and a summary is the id the runtime reported (Claude: the `model` of the `system`/`init` event; Pi: `provider/model` of the first assistant message), never the `--model` flag. An eval's model is the single id its runs reported; none, or a mix, is recorded as `unknown`. `unknown` is not comparable to anything, itself included, so a summary with an unknown model is never written unless `--update-baselines` is given. Summaries of package granularity (Claude) also carry `packageHash`; a changed `packageHash` is a printed note, not a reason for `not-comparable` (see Comparison below). For skill-level Pi the field is informational only (recorded when present, not compared): Pi loads one skill, which `skillHash` already covers.

*When a summary is written.* The run prints the check status per eval and writes `evals/baselines/<runtime>/<skill>.json` only when the status is `no-baseline` or `ok` and the model is known, or when `--update-baselines` is given. A `regression` (committed summary reliable, new one not) prints `REGRESSION ...` on stderr and makes the run exit 1; it never overwrites the committed file by itself, and with `--update-baselines` the file is replaced but the exit stays 1. A `not-comparable` result (different model, runtime, eval version or repeats) prints why, leaves the file alone and does not change the exit code unless `--update-baselines` replaces it. Exit codes: 2 (a rejected definition, a result or baseline that could not be stored or read, an evaluated copy that could not be hashed) outranks 1 (a failing eval or a regression), which outranks 4 (incomplete); the run reports both when they coincide.

*Integrity of the store.* Reading and writing baselines refuse a symlink in the baselines root, the runtime directory or the file (named error), skip nothing silently, reject a non-regular file (FIFO, device) and a file over 1 MiB before reading it, and write through a temp file and an atomic rename inside the verified directory. A summary must be self-consistent or it is rejected naming the file and field: each arm has at least one run, both arms ran `repeats` times, `bar <= repeats`, `reliable` equals `withSkill.passes >= bar`, and `uplift` equals the arm pass-rate difference within 1e-9. The report refuses to print a rate for an arm with no run (a named error, never `NaN%`).

*Sanitising.* The whole suite log (results, `claudeResult`, `stderr`, `changedFiles` and records), not only the records, is scrubbed of credentials and of the author's machine: the repository root (as given and its realpath) becomes `<repo>`; home directories, `/Users/<name>`, `/home/<name>`, `/root` and `C:\Users\<name>` become `~`; the OS user name and host name become `<user>` and `<host>` when they appear as a path component or a word of at least 4 characters. An eval's records are built in a local list and appended only when all of them built, so a failed eval leaves no partial records; an evaluated copy that cannot be hashed rejects that eval (skipped, exit 2 at the end) instead of aborting the suite.

**Report.** Per skill: with-skill rate, baseline rate, uplift (the difference, a number only) and the reliability verdict of the with-skill arm against its bar. Claude uplift is labelled `package-level (skills share a package)` and Pi uplift `skill-level`; when a report holds both it says they are different quantities. An eval with a run that did not execute, a baseline run whose isolation could not be verified, or an aborted baseline is marked INCOMPLETE (or ABORTED) with the reasons and shows no rate, uplift or verdict.

**Coverage.** `node evals/coverage.js` reports each shipped skill once as evaluated, exempt (reason shown) or missing. `evals/exemptions.json` is a plain `{ "<skill>": "<reason>" }` map; it starts with the 17 `adapter-*` skills, which a toolchain resolver loads and nobody invokes by name. Only `missing` counts against coverage. The report is not trusted (exit 2) when the file is unreadable, repeats a key, exempts a skill that does not exist or already has an eval, a source package is a symlink or holds a symlinked `skills/` directory, a symlinked, nameless or duplicated skill, or a stray non-directory entry in `skills/` (`.gitkeep` and `.DS_Store` aside), or an eval names a skill no source package ships. An exemption for a skill whose eval was rejected still shows the rejection; control characters and ANSI sequences are stripped from exemption reasons before they are printed.

## Cache, comparison and replay (PR 6)

How a maintainer spends nothing on unchanged work, checks a result against the committed baseline, and reruns a failure. Reference for the flags: `evals/README.md`.

### Result cache

`node evals/run.js --skill <skill> --model <id>` reuses a stored per-run result when the skill hash (Claude: the package hash, because the whole package is loaded; Pi: the skill hash), the eval version, the requested model, the runtime, the arm, the invocation mode, the repeat index and the run settings (`maxTurns`, `allowedTools`, timeout, per-run budget, judge model) are all the same. Reuse makes no model call and costs nothing against the suite cap. A stored result of any age is reused; `--refresh` forces fresh runs. Decisions the design leaves open, as taken:

- **The model in the key is the requested `--model`.** The model a runtime reports exists only after the call, so the key cannot hold it; a stored result is reused only when the model it reported is known. With no `--model` the cache is bypassed (read and write) and the run says so, because a default model can change without any input changing.
- **The per-run budget and timeout are in the key.** `--max-usd` can lower the per-run budget, so a very low cap is a different key. Raising a timeout reruns; that is the price of never reusing a result produced under different limits.
- **Isolation evidence is stored with a baseline-arm entry and checked again on read**; missing evidence is a miss (a stored result has no startup event to re-verify, so absence is never read as clean).
- **A regression is not stored** (unless `--update-baselines`): a failing result is not locked in as the reusable answer. Per-run entries are otherwise written as the runs finish, including for a not-comparable result (that is a different key space: model, eval version and so on differ).
- **The cache is a store.** Same rules as the baselines: symlinked root, runtime directory or entry refused, FIFOs never opened, size cap, write through a temp file and rename. Read-back entries are untrusted: validated field by field, a bad one is a miss.

### Comparison and regression

`npm run evals:compare` reads the newest results log and prints, per eval, one of: the change in with-skill rate and uplift (comparable), a regression (exit 1, naming skill and eval), `NOT COMPARABLE` or `NOTHING COMPARABLE` (no regression claimed), or `INCOMPLETE` (exit 4). The comparable key is **runtime, model, eval version and repeats**, as the TRD says. This reverses an earlier PR 5 decision that also treated a changed Claude package hash as not comparable: with the cache keyed on that hash, a comparable result would almost always have been a cache hit, so the check could only see its own numbers and a deliberately broken skill would have read as not comparable, a gate that cannot fail (Constitution rule 7). A changed skill or package hash is now a printed note. The PRD's AC-016-1 says "skill version"; the TRD's like-for-like list (runtime, model, eval version) was followed, and a changed `metadata.version` is also a note.

### Replay

A failing run prints a command (see `evals/README.md`) that reruns exactly that run: same eval, arm, runtime, requested model, repeat index and settings. It is single-quoted throughout, built from validated fields, and carries no secret or machine path. `--arm`/`--run-index` run only that run, fresh, without cache or baseline effects. Credentials must be present in the environment as for the original run; `--allow-env` and `--env-allowlist` are deliberately not part of the command.

## CI, credential guard and proof the gate can fail (PR 7)

**Local and CI parity.** The workflow `.github/workflows/evals.yml` calls the same npm scripts a maintainer runs: `npm run evals -- --runtime <runtime> --model <model> --max-usd <usd> [--skill <skill>]`, `npm run evals:coverage` and `npm run evals:compare [-- --skill <skill>]`. They produce the same report and comparison locally and in CI; the run log and report are uploaded as the `eval-results` artifact.

**On demand only.** The workflow is `workflow_dispatch` with the inputs `skill` (blank runs the full suite), `runtime` (`claude` or `pi`), `model` and `max_usd`. It has no `push`, `pull_request` or `schedule` trigger: changing a skill or an eval does not run it unless a maintainer triggers it. The `pi` runtime needs the Pi CLI on the runner; the workflow installs only the Claude Code CLI.

**Advisory, not required.** The regression check is advisory. When a committed reliable eval is no longer reliable the `Regression check` step fails and names the skill and eval, but the evals workflow is not a required status check on any protected branch and does not block merging. Do not make it one: it needs credentials and a model, which a required check on a pull request must never have.

**Credential guard.** Dispatch inputs are passed to the shell only as environment variables and quoted arguments (never expanded inside a `run:` script). The job and the step that uses `secrets.ANTHROPIC_API_KEY` run only when `github.repository` is this repository and `github.ref` is `refs/heads/main` or `refs/heads/dev`, so a fork's dispatch, a tag, a pull ref and an unmerged feature branch receive no secrets: a dispatch runs the code at the dispatched ref with the key, so only branches whose changes were reviewed may carry it. `.github/CODEOWNERS` lists `/evals/` explicitly so an eval or fixture change is reviewed like code when it is proposed for those branches (CODEOWNERS applies to pull requests, not to a dispatch). For defence in depth, store `ANTHROPIC_API_KEY` as a secret of a GitHub Environment whose deployment branches are limited to `main` and `dev`, and add `environment:` to the job; that is a repository setting this change cannot make. The regression-check step is skipped for the legacy `scenario` input, which produces no skill evals to compare. The workflow has `contents: read` permissions only.

**Proof the gate can fail.** `evals/tests/regression-gate.test.js` copies the `ensemble-create-prd` package into a scratch directory (`EVALS_REPO_ROOT`), runs a content-sensitive stub (it passes only when the skill still contains a required instruction) and records a reliable baseline. With one instruction broken, `run.js` and `compare.js` exit 1 naming the skill and eval; with the defect removed they pass. The inverse proofs (a stub that ignores the content, no baseline, an unreliable baseline) show the failure comes from the defect and that the check does not claim a regression without a reliable like-for-like baseline.

## Pilot evals (PR 8)

The four pilot skills have evals under `evals/skills/`. This section says what each checks and what it cannot. Pilot run size: Claude 4 evals, Pi 2 (`ensemble-create-prd` and `ensemble-refine-prd`; a search of their skill directories finds no CLI, `*-cli` or `CLAUDE_PLUGIN_ROOT` reference, so no CLI-resolution dependency was found for them on Pi: not proven by a Pi run). It states no measured result: the with-skill and baseline numbers, reliability and cost of the pilot run are recorded separately, once that run has been made.

Common to all four: prompts are non-interactive, foreman-style (`--foreman`, no questions); the command is typed first in the with-skill arm (`invocation: explicit`; `pr-merge-trace` uses `explicit-both`); the checks run `evals/checks/pilot-checks.js` and print `PASS:` or `FAIL: <reason>` (the reason appears in the stored check detail). The fixture holds a minimal `docs/standards/constitution.md` with article headings, because the Constitution Gate halts with `CONSTITUTION_CONFIG_ERROR` without one. For the three document evals the baseline arm is expected to pass or fail on its own merits: a model that knows the format can pass some checks without the skill, and the difference is the uplift. `pr-merge-trace` is the exception (see its loading paragraph).

**`pr-merge-trace` loading and what its uplift means.** The skill lives in `packages/development`; the command it records, `/ensemble-git:ensemble:pr-merge`, in `packages/git`. Each job carries `pluginDirs`: the baseline `packages/git` only (the command is there, the skill is not), the with-skill arm `packages/git` then `packages/development`. The `toolchain-cli` the skill uses is also in `packages/development`. By the files: step 1.1 of `packages/git/skills/ensemble-pr-merge/SKILL.md` resolves `toolchain-cli` through the `tool-path-resolution` tiers (the git top level, the working directory, `${CLAUDE_PLUGIN_ROOT}`), and those tiers fail in the sandbox for the baseline arm, which loads `packages/git` only. **The baseline therefore certainly halts at step 1.1, before any `gh` call, and fails every check.** Whether the with-skill arm resolves `toolchain-cli` depends on `${CLAUDE_PLUGIN_ROOT}` substitution, which is **unproven**: the sandbox is a separate repository, `packages/git` has no `lib/toolchain-cli.js`, and no other tier obviously reaches `packages/development/lib/`. So any uplift measured here may reflect the package being present, not the skill: **the result is not skill-attributable** until a trial shows the with-skill arm gets past step 1.1. **Required before the pilot counts:** a maintainer-run trial (a real run, no stub model, one repeat) of `pr-merge-trace`; if the with-skill arm halts at step 1.1 too, the eval measures nothing until the way the command finds `toolchain-cli` is settled. Giving the path to both arms is not an option, because it would hand the baseline the tool the skill needs. The eval's `description` and the report label (`package-level (with-skill adds development)`) carry this.

**The `gh` stub.** `fixture/bin/gh` answers from `fixture/bin/canned/*.json`, in the shape `gh` prints after applying `--jq` (the stub does not run `jq`): `--version`, `auth status`, `repo view`, `pr view` (the adapter's field list, the comments call and a generic object), `pr checks`, `api graphql` (the review state: human `CHANGES_REQUESTED`, one unresolved thread), `api repos/.../commits/.../status` (no status) and `pr merge`. Every call is appended to `gh-calls.log` in the sandbox root as one line holding its full argv (a newline or carriage return inside an argument is folded to a space, so a multi-line GraphQL query stays on one line and a crafted argument cannot fake the start of another call), outside the project's git worktree, so `git add -A` and `git clean` cannot capture or delete it. Any other call exits 2 with a message on stderr. The eval's `sandboxPath: ["bin"]` puts the fixture's `bin/` first on the agent's PATH only (never the checks' PATH, so a `node` planted there cannot stand in for the real one). A command that calls `gh` by absolute path bypasses the stub. `.ensemble/toolchain.yaml` pins `host: github`, because a local bare origin matches no host and detection would otherwise be ambiguous. The eval's `remote: true` creates the bare `origin` and `branch: "fix/slugify-trim"` checks out the PR's head branch (and pushes it), so the head the canned PR names exists locally and on origin and `main` stays unchecked-out and untouched.

**What the tests prove.** `evals/tests/pilot-evals.test.js`: each eval loads and its fixture holds a constitution file; conforming stub output passes every check and bad output (no ACs, changed Document ID, no TRD, no trace) fails the matching check; the host adapter really runs against the stub; a stub `claude` recording its argv shows the baseline `--plugin-dir` for `packages/git` only and the with-skill arm for both, with `gh` resolving to the sandbox stub; a `node` planted in `bin/` cannot spoof the checks. The review-fix tests also cover: graphql merge mutations and the `pr view` first-words rule in `gh-no-merge`, the stub's one-line-per-call log, the uplift label naming added packages, the working-tree status over shared packages (`evals/tests/arms.test.js`), and `sandboxPath` validation for legacy scenarios (`evals/tests/eval-def.test.js`; a legacy scenario's `sandboxPath` goes through the same function as a skill eval's, so an absolute or `..` entry fails the load).
