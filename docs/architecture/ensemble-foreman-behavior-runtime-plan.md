# Ensemble + Foreman Behavior Runtime

## Future Design, Requirements, and Delivery Plan

- **Status:** Proposed
- **Date:** 2026-09-23
- **Scope:** Ensemble and Foreman
- **Primary runtime:** Pi/OMP
- **Durable orchestration runtime:** Foreman
- **Audience:** Maintainers of Ensemble, Foreman, and integrations built on both

---

## 1. Executive decision

Ensemble and Foreman should diverge into two coordinated products rather than merge into one codebase or remain two competing orchestration systems.

### Ensemble becomes the behavior system

Ensemble should own the portable, authorable definition of project behaviors:

- event patterns and predicates;
- behavior policies and safety declarations;
- behavior composition;
- tool and provider capabilities;
- constitutions and learning artifacts;
- local execution and simulation;
- Pi/OMP packaging;
- behavior validation, fixtures, and conformance tests.

Ensemble should not own durable production scheduling when deployed with Foreman.

### Foreman becomes the durable behavior control plane

Foreman should own the operational execution of behaviors:

- event ingestion and normalization;
- behavior activation and deduplication;
- durable causal history;
- leases, budgets, retries, and concurrency;
- worktrees and VCS operations;
- approvals and mutation governance;
- execution graphs;
- agent dispatch;
- projections, dashboards, recovery, and operator controls.

Foreman should not become a behavior-authoring monolith or embed Pi/OMP-specific concepts throughout its domain model.

### Pi/OMP becomes the agent execution substrate

Pi/OMP should provide the agent loop and invocation capabilities:

- model/provider abstraction;
- sessions;
- steering and follow-ups;
- custom tools;
- agent lifecycle events;
- subagents;
- tool-call execution;
- invocation-local state.

Pi/OMP should not become the durable event store, scheduler, policy ledger, or project execution database.

### The governing rule

For a Foreman deployment there must be exactly one durable behavior coordinator: **Foreman**.

Ensemble may compile, validate, simulate, and package behaviors. Pi/OMP may execute an agent invocation. Neither may independently dispatch durable behavior activations inside Foreman.

## 2. Product model

The systems should use these distinct concepts.

| Concept | Definition | Owner |
|---|---|---|
| Event | Immutable fact that something happened | Foreman ingress/domain layer |
| Behavior | Versioned rule describing what should happen in response to events | Ensemble definition layer |
| Policy | Safety, authority, budget, and approval constraints for a behavior | Ensemble declares; Foreman enforces |
| Activation | Durable decision that a behavior matched an event and was admitted, suppressed, or blocked | Foreman |
| Execution | One durable attempt to perform an activation | Foreman |
| Agent invocation | One Pi/OMP or other backend execution within an execution step | Agent runtime |
| Tool | Governed capability available to an invocation | Foreman policy + Pi/OMP adapter |
| Workflow | A reusable sequence or graph of execution steps | Foreman execution layer; optionally generated by Ensemble |
| Constitution | Project policy and durable engineering guidance | Ensemble artifact; Foreman snapshots and governs mutations |
| Proposal | A reviewable suggested change to code, constitution, behavior, or policy | Foreman projection/domain layer |
| Outcome | Facts emitted after execution, including proposals, mutations, or failures | Foreman |

A command is an invocation surface. A behavior is a durable reaction. A skill is reusable agent guidance. A workflow is an execution mechanism. These terms must not be collapsed.

### Example: test-failure behavior

```text
test.failed event
  -> normalize failure identity
  -> match investigate-test-failure behavior
  -> evaluate cooldown, budget, recursion, and mutation policy
  -> create BehaviorActivation
  -> create bounded investigation execution
  -> run Pi/OMP with read/test tools
  -> classify root cause
  -> produce evidence and regression-test proposal
  -> produce constitution-amendment proposal
  -> require approval for constitution mutation
  -> apply only approved mutations
  -> emit behavior outcome and learning event
```

The default behavior must **not** directly edit a constitution merely because an agent believes the edit is useful.

### 3.1 Ensemble package format

Add a first-class behavior package format without removing existing command, agent, or skill formats.

Recommended layout:

```text
packages/<domain>/behaviors/<behavior-id>/
├── behavior.yaml
├── prompts/
├── skills/
├── fixtures/
│   ├── events/
│   ├── expected-matches/
│   └── expected-outcomes/
├── constitution-rules.yaml
└── README.md
```

Example:

```yaml
api_version: ensemble.sunstone.dev/v1
kind: Behavior
metadata:
  name: investigate-test-failure
  version: 1.0.0
  description: Investigate repeated test failures and propose durable prevention.

trigger:
  event_type: test.failed
  predicate:
    command: { matches: "npm test|mix test|pytest|go test" }
    exit_code: { not: 0 }

policy:
  mode: propose
  max_concurrent: 1
  cooldown: 24h
  max_causal_depth: 2
  max_children: 3
  timeout: 30m
  retry:
    max_attempts: 2
    retryable: [agent_error_retryable, worker_timeout]

capabilities:
  tools: [read, grep, glob, bash.test, git.diff]
  mutation_classes: [artifact.write, pr.open, constitution.propose]

execution:
  graph: investigate-test-failure

outcomes:
  - test.failure.investigated
  - constitution.change.proposed
```

The schema must distinguish `capabilities.tools` from `policy.mutation_classes`. A tool grant does not imply authority to perform every mutation reachable through that tool.

### 3.2 Foreman domain additions

Add a behavior subsystem under `ForemanServer.Behavior` with these durable concepts:

```text
Behavior.Definition       # validated immutable snapshot
Behavior.Event            # normalized event envelope
Behavior.Activation       # match/admission decision
Behavior.Execution        # causal execution record
Behavior.PolicyDecision   # allow, suppress, block, or require approval
Behavior.Proposal         # reviewable mutation proposal
Behavior.Budget           # token, time, fan-out, and tool budget
Behavior.CausalLink       # parent/child activation relationship
Behavior.Deduplication    # stable idempotency and cooldown state
```

Recommended modules:

```text
ForemanServer.Behavior.Catalog
ForemanServer.Behavior.EventNormalizer
ForemanServer.Behavior.Matcher
ForemanServer.Behavior.Policy
ForemanServer.Behavior.Activator
ForemanServer.Behavior.ExecutionGraph
ForemanServer.Behavior.Reconciler
ForemanServer.Behavior.Proposal
ForemanServer.Behavior.Projector
```

The behavior subsystem must use the existing command gateway and event store. It must not write projections directly and must not introduce a second event database.

### 3.3 Event envelope

All behavior-triggering events must be normalized into a stable envelope:

```elixir
%{
  event_id: binary(),
  event_type: binary(),
  occurred_at: DateTime.t(),
  source: binary(),
  project_id: binary() | nil,
  subject_id: binary(),
  payload: map(),
  schema_version: pos_integer(),
  correlation_id: binary() | nil,
  causation_id: binary() | nil,
  actor: %{type: atom(), id: binary() | nil},
  deduplication_key: binary()
}
```

The event ID identifies one fact. The deduplication key identifies semantically equivalent triggers. These must not be conflated.

### 3.4 Agent runtime boundary

Retain `ForemanServer.AgentRuntime` as the only public invocation boundary.

Implement Pi/OMP as a first-class backend adapter:

```elixir
ForemanServer.AgentRuntime.Adapters.PiOmpAdapter
```

The adapter should translate a provider-neutral invocation request into Pi/OMP concepts and return provider-neutral results. Pi/OMP types must not leak into aggregates, projections, behavior definitions, or workflow manifests.

The invocation request should include:

```elixir
%{
  execution_id: binary(),
  prompt: binary(),
  context: map(),
  tools: [tool_id()],
  worktree: worktree_spec() | nil,
  model: model_alias() | nil,
  timeout_ms: pos_integer(),
  attempt: pos_integer()
}
```

The result should include only normalized output, status, usage metadata, and structured tool/outcome records. It must not expose raw provider sessions as domain state.

### 3.5 Tools and governance

Tools should be registered through a provider-neutral capability registry and resolved at execution time.

Every tool must declare:

- stable ID and version;
- read/write classification;
- required authority;
- supported contexts;
- input schema;
- output schema;
- idempotency characteristics;
- side effects;
- cancellation behavior;
- audit fields;
- whether approval is required.

Recommended mutation classes:

```text
read.repository
read.logs
execute.tests
write.artifact
write.source
vcs.commit
vcs.push
pr.open
pr.merge
constitution.propose
constitution.apply
behavior.propose
behavior.apply
policy.propose
policy.apply
```

A behavior may request capabilities, but Foreman resolves the effective grant from project policy, operator policy, and execution context.

### 3.6 Execution graph

Use Foreman’s existing run, phase, worker, worktree, slot, lease, retry, and projection machinery as the initial execution substrate.

Do not immediately replace `RunExecutor` with a new generalized engine. Instead:

1. compile a behavior activation into an existing run/workflow;
2. persist behavior and causal metadata alongside the run;
3. add graph execution only where real behaviors require branching, parallelism, waiting, or child activation;
4. then extract generalized graph scheduling from the proven path.

This is compatible with the existing Foreman-native work graph direction. The graph must reuse `RunSlots`, not introduce a second concurrency budget.

### 3.7 Constitution handling

Constitutions are versioned project artifacts. A behavior may:

- read the constitution automatically when policy permits;
- identify a violated or missing rule;
- produce a structured amendment proposal;
- attach evidence and regression tests;
- request approval;
- apply only an approved amendment through a command gateway.

Every amendment must record:

- source behavior and version;
- triggering event;
- evidence references;
- proposed diff;
- approving actor;
- resulting constitution version;
- affected projects or behaviors;
- rollback/reversion information.

## 4. Functional requirements

### Behavior definitions

**REQ-BEH-001 — Versioned definitions.** Every behavior must have a stable ID, semantic version, schema version, and immutable execution snapshot.

**REQ-BEH-002 — Typed triggers.** A behavior must declare one or more event types and predicates. Matching must be deterministic and testable without an agent invocation.

**REQ-BEH-003 — Explicit policy.** A behavior must declare timeout, retry, concurrency, cooldown, fan-out, causal-depth, mutation, and approval policy. Missing safety fields must resolve conservatively.

**REQ-BEH-004 — Portable compilation.** Ensemble must compile a valid behavior package for local Pi/OMP execution and for Foreman deployment without changing behavior semantics.

**REQ-BEH-005 — Compatibility validation.** Compilation must fail when a behavior requests unsupported tools, mutation classes, event schemas, or runtime features.

### Eventing and activation

**REQ-ACT-001 — Idempotent ingestion.** Re-delivery of an event must not create duplicate activations.

**REQ-ACT-002 — Stable deduplication.** Deduplication keys must be derived from event identity, subject, behavior version, and declared behavior-specific identity fields.

**REQ-ACT-003 — Cooldowns.** Behaviors must support project-, subject-, and behavior-scoped cooldowns.

**REQ-ACT-004 — Explicit decisions.** Every match must produce an auditable decision: activated, suppressed, blocked, rejected, or failed.

**REQ-ACT-005 — Causal limits.** A behavior-triggered event must not recursively activate unbounded behavior chains. Enforce maximum causal depth and per-root fan-out.

**REQ-ACT-006 — Reconciliation.** A restart or dropped notification must not strand eligible activations. Boot reconciliation must reconstruct pending work from the event stream and projections.

### Execution

**REQ-EXE-001 — Bounded work.** Every execution must have time, token/model, tool-call, child-count, and concurrency budgets.

**REQ-EXE-002 — Durable lifecycle.** Activation and execution lifecycle transitions must be event-sourced and projected.

**REQ-EXE-003 — Fresh attempts.** Retry must use a fresh worker/session and the declared worktree semantics. Non-idempotent mutations are not automatically retried.

**REQ-EXE-004 — Leases.** Event processing, behavior activation, project execution, and external database writes must use explicit leases where required. Lease ownership and expiry must be durable and observable.

**REQ-EXE-005 — Operator control.** Operators must be able to pause, resume, cancel, retry, abandon, and inspect a behavior execution using the existing command boundary.

**REQ-EXE-006 — Provider neutrality.** A behavior must not require Pi/OMP-specific fields unless it declares a runtime-specific extension and passes compatibility validation.

### Safety and governance

**REQ-SAFE-001 — Read before mutate.** Mutation actions must require evidence and a policy decision before execution.

**REQ-SAFE-002 — Approval gates.** Constitution, behavior-definition, tool-policy, merge, and production-impacting changes must be approval-gated by default.

**REQ-SAFE-003 — Auditability.** Every tool call, policy decision, proposal, approval, mutation, and emitted event must be attributable to an execution and causal root.

**REQ-SAFE-004 — Secret isolation.** Prompts, logs, projections, and behavior events must not expose credentials, tokens, or unrestricted command output.

**REQ-SAFE-005 — Recursion prevention.** A behavior must not activate itself or a configured recursive cycle without an explicit bounded policy.

**REQ-SAFE-006 — Safe failure.** If policy, catalog, lease, or capability resolution fails, the system must suppress or block the behavior rather than execute with expanded authority.

### Compatibility

**REQ-COMP-001 — Existing commands remain usable.** Existing Ensemble commands, skills, and generated Pi artifacts continue to work during migration.

**REQ-COMP-002 — Existing Foreman workflows remain usable.** Ungraphed tasks and current workflow manifests must behave identically unless explicitly opted into behaviors.

**REQ-COMP-003 — Existing adapters remain usable.** Jido Harness remains available during Pi/OMP migration; both adapters implement the same runtime contract.

**REQ-COMP-004 — No dual dispatch.** In Foreman mode, only Foreman activates durable behaviors. Ensemble local dispatch must be disabled or explicitly local-only.

## 5. Delivery strategy

Each sprint is intended to be two weeks with one cross-repository integration checkpoint. Work may be parallelized, but the dependency order below is mandatory.

### Sprint 0 — Architecture ratification and measurement

**Outcome:** Freeze vocabulary, boundaries, and baseline behavior.

#### Stories

- **S0-1:** As a maintainer, I can distinguish event, behavior, activation, execution, workflow, skill, command, tool, and constitution in the architecture docs.
- **S0-2:** As a maintainer, I can compare current Ensemble and Foreman behavior without inventing unsupported runtime capabilities.
- **S0-3:** As an operator, I have baseline measurements for current workflow startup, Pi/OMP invocation cost, Jido invocation cost, event volume, and worktree cost.

#### Tasks

- Ratify the ownership table in this document.
- Inventory current Ensemble command/skill/agent sources that should become behaviors.
- Inventory Foreman event types suitable for normalized behavior triggers.
- Define the initial behavior schema and event envelope.
- Record Pi/OMP and Jido adapter capability matrices.
- Measure one long-running agent loop versus multiple Foreman graph nodes.
- Define the initial mutation-class policy table.

#### Tests

- Architecture lint: no Foreman behavior module directly imports Pi/OMP types.
- Architecture lint: no Ensemble deployment adapter writes Foreman event-store state.
- Golden test: existing generated Pi artifacts are unchanged.
- Baseline integration test: existing Foreman task-to-run path is unchanged.

#### Spike

**S0-SP1 — Pi/OMP invocation adapter proof.** Build a throwaway adapter that starts one Pi/OMP session, registers one custom tool, captures lifecycle events, and returns normalized output. Do not commit provider-specific types into Foreman domain modules.

**Exit gate:** Architecture is ratified; adapter proof passes; no implementation begins if the boundary is ambiguous.

## 6. Non-functional requirements

### Reliability

- Every durable transition is replayable.
- Every external event has an idempotency strategy.
- Dropped broadcasts are recoverable through reconciliation.
- Worker crashes do not corrupt activation state.
- Retries are bounded and policy-controlled.

### Safety

- Default behavior mode is `propose` for repository policy and constitution changes.
- Unknown tools, mutation classes, event schemas, and policy fields fail closed.
- No behavior may expand its own authority.
- No recursive behavior chain may run without explicit depth and fan-out bounds.
- Approval-gated mutations must remain blocked across restarts until approved.

### Observability

Every activation and execution must be searchable by:

- behavior ID/version;
- event ID and deduplication key;
- project and subject;
- causal root and parent activation;
- run and worktree;
- policy decision;
- agent backend and model alias;
- tool calls;
- proposal and approval IDs;
- final outcome.

### Performance

- Matching must not require an agent call.
- Normalized event handling must be bounded and non-blocking relative to event-store writes.
- Behavior catalog loading must not block existing task dispatch indefinitely.
- Scheduling must remain deterministic under equivalent event histories.

### Compatibility

- Existing Ensemble artifacts remain supported during the migration window.
- Existing Foreman workflows continue to run without behavior metadata.
- Jido Harness remains a supported adapter until Pi/OMP parity is demonstrated.
- Existing APIs gain additive behavior fields before any breaking changes.

## 7. Explicit non-goals

The following are not part of the first implementation:

- replacing every Ensemble command with a behavior;
- replacing every Foreman workflow with a graph;
- embedding a complete durable scheduler inside Pi/OMP;
- making constitutions self-modifying without approval;
- making Foreman parse arbitrary TRDs into execution graphs;
- moving Beads backlog semantics into Foreman;
- requiring one universal behavior DSL for every runtime;
- removing Jido Harness before Pi/OMP adapter parity is measured;
- allowing arbitrary behavior code to execute in the event matcher.

---

## 8. Migration and deprecation policy

### Stage 1: additive

- Add behavior schema, compiler, catalog, event envelope, and adapter.
- Existing commands and workflows remain primary.
- New behavior dispatch defaults to shadow mode.

### Stage 2: opt-in

- Enable behaviors per project and per behavior.
- Preserve command aliases as compatibility wrappers that create explicit activations or invoke existing workflows.
- Record equivalence metrics.

### Stage 3: behavior-first

- New autonomous capabilities must be implemented as behaviors unless they are strictly interactive commands or reusable skills.
- Commands remain user-facing shortcuts and inspection/control surfaces.
- Workflows remain implementation graphs where useful.

### Stage 4: selective removal

Remove duplicated command logic only after:

1. an equivalent behavior exists;
2. migration documentation exists;
3. shadow and opt-in production evidence exists;
4. rollback is tested;
5. the compatibility window has elapsed.

---

## 9. Definition of done for the program

The Ensemble/Foreman behavior runtime is ready for general use when all of the following are true:

- A behavior can be authored, validated, versioned, and compiled by Ensemble.
- Foreman can load and snapshot the behavior definition.
- A normalized event can produce one deterministic activation decision.
- Duplicate delivery, cooldowns, leases, recursion, and budgets are enforced.
- An activation can run through Pi/OMP behind the provider-neutral AgentRuntime boundary.
- Existing Jido-backed workflows still work.
- The complete causal chain is visible in projections and dashboards.
- Constitution and behavior changes are proposal/approval-gated.
- Restart, retry, cancellation, and reconciliation are tested.
- At least two pilot behaviors operate in shadow mode and one operates in opt-in active mode.
- Measured cost and latency are acceptable relative to the command/workflow baseline.

## 10. Final recommendation

Proceed with the split immediately:

```text
Ensemble  -> behavior language, packages, policy declarations, local Pi/OMP harness
Foreman   -> durable event-driven behavior control plane and execution supervisor
Pi/OMP    -> agent loop and tool invocation substrate
```

Do not fork Foreman into Ensemble. Do not make Pi/OMP the durable orchestrator. Do not build a second dispatcher in Ensemble that competes with Foreman.

The first production slice should be deliberately narrow:

```text
test.failed -> investigate-test-failure -> bounded Pi/OMP run -> proposal
```

It should end in an evidence-backed proposal, not an automatic constitution edit. That slice exercises the entire architecture—events, matching, policy, activation, execution, tools, worktrees, proposals, approvals, projections, and recovery—without granting the system unbounded authority.
