# Behavioral evals

Headless harness that checks what models *do* with Ensemble instructions. Deterministic checks decide every verdict; an optional model-judged check adds a separate score and never changes it.

## Run

```bash
npm run evals -- --dry-run                      # list scenarios
node evals/run.js --scenario fix-issue --model sonnet --max-usd 1
node evals/run.js --max-usd 5                   # all scenarios
node evals/run.js --concurrency 2 --timeout 600 --keep-workspace
node evals/run.js --skill <skill> --runtime claude --repeats 3   # with-skill and baseline arms, repeated
node evals/run.js --skill <skill> --model <id> --refresh         # ignore stored results, run fresh
npm run evals:coverage                                           # which shipped skills have an eval (same report the workflow uploads)
npm run evals:compare                                            # newest results log vs the committed baselines (read-only)
npm run evals:compare -- --skill <skill>                         # only that skill
```

## CI (on demand, advisory)

`.github/workflows/evals.yml` is `workflow_dispatch` only: a maintainer runs it from the Actions tab with the inputs `skill` (blank = the full suite), `runtime` (`claude` or `pi`), `model` and `max_usd` (plus the legacy `scenario`). There is no `push`, `pull_request` or `schedule` trigger, so a change to a skill or an eval never runs it on its own. Its steps are the same entry points a maintainer runs locally with the same arguments: `npm run evals -- --runtime <runtime> --model <model> --max-usd <usd> [--skill <skill>]`, then `npm run evals:coverage`, then `npm run evals:compare [-- --skill <skill>]`. `evals/results/` (the log and the report) is uploaded as the `eval-results` artifact.

- **Advisory.** A regression makes the `Regression check` step fail (exit 1, naming skill and eval) and the run shows red, but the regression check is advisory: the evals workflow is not a required status check on any protected branch and blocks no merge. Do not add it as one.
- **Credential guard.** Inputs reach the shell only as environment variables (`EVAL_SKILL`, `EVAL_RUNTIME`, `EVAL_MODEL`, `EVAL_MAX_USD`), never expanded inside a script body. The job and the step that reads `secrets.ANTHROPIC_API_KEY` run only when `github.repository` is this repository and `github.ref` is `refs/heads/main` or `refs/heads/dev`; a fork's dispatch, a tag, a pull ref and an unmerged feature branch get no secrets (a dispatch runs the code at its ref with the key). `.github/CODEOWNERS` has an explicit `/evals/` owner so an eval or fixture change is reviewed like code when proposed for those branches. Permissions are `contents: read`.
- **The gate can fail.** `evals/tests/regression-gate.test.js` copies a skill package, breaks one instruction, runs a content-sensitive stub against a reliable baseline and requires the check to fail (and to pass again once the defect is removed).

Agent scenarios shell out to `claude -p` through the Claude adapter (`lib/runners/claude.js`: stream-json, `--setting-sources project`, `--plugin-dir packages/<pkg>`, `--max-turns`, `--allowedTools`, `--permission-mode`) inside a throwaway git repo built from the scenario fixture under `EVALS_WORKDIR`. `cli` scenarios run no model.

Without the `claude` CLI (override path with `EVALS_CLAUDE_BIN`): `--dry-run` prints a skip message and exits 0 (2 if a skill eval definition was rejected); a real run exits 3. Test hooks: `EVALS_SCENARIOS_DIR`, `EVALS_SKILLS_DIR`, `EVALS_RESULTS_DIR`, and `EVALS_REPO_ROOT` (read once by `run.js`: the repository whose `packages/` are loaded and hashed, so a test can edit a scratch copy of a skill package; it must be an existing directory containing `packages/`, else exit 2).

## Safe execution

Each run works in its own throwaway directory, is budgeted, and its stored output is stripped of credential values. This is a directory sandbox, not an OS jail: the agent runs as you and can reach anything your user can, including files under the real `HOME` when it is passed through (see Environment).

- **Workspace.** Each run works in a fresh copy of the fixture under `EVALS_WORKDIR` (default `~/.omp/evals-work/`; `/tmp`, `$TMPDIR`, `/var/folders` and anything inside the repository are refused, after resolving symlinks). The repository is never touched. The workspace is removed afterwards; `--keep-workspace` keeps it and prints `workspace kept: <path>`.
- **Environment.** The agent and the judge call see only `PATH`, `LANG`, `TERM`, `TMPDIR`, `HOME` and the named credentials; nothing else is inherited. An eval's `sandboxPath` (also a legacy scenario's, validated by the same function: relative, inside the fixture, an existing directory; otherwise the scenario fails to load) puts fixture directories (a stub binary such as `bin/gh`) in front of the agent's `PATH` only, never the checks' or the judge's. The checks that execute agent-written code or commands (`testsPass`, `commandOutputMatches`, `trdParses`) get the same environment with **no credentials**; only the agent and the judge get those. `HOME` passes through to the agent on a maintainer's machine so the CLI's own login works, which means the agent can read and write files under your real home directory; with `CI=true` or `GITHUB_ACTIONS=true` it is a fresh per-run directory under `EVALS_WORKDIR`, removed afterwards. The credential-free checks never get your real `HOME`: they always run with a throwaway empty `HOME` under `EVALS_WORKDIR` (in CI, the same per-run directory). Under `--runtime pi` the judge (a `claude` process) never receives the Pi provider keys named under `runtimes.pi`, and Pi runs use a throwaway empty `HOME` like the checks. Credential names live in `evals/env-allowlist.json` (`{"credentials": ["ANTHROPIC_API_KEY"], "runtimes": {"pi": [...]}}`; names under `runtimes.<name>` reach only that runtime's runs); add names per run with `--allow-env NAME` (repeatable) or use another file with `--env-allowlist FILE` (the file must exist). A credential reaches the agent from the local environment, or from CI secrets exported by the workflow. The harness's own `git` calls in the workspace use a sanitized environment (no `GIT_*`, no system or global config) with `core.fsmonitor`, `core.hooksPath`, `core.pager`, `core.gitProxy` and `protocol.ext.allow` neutralised (and `core.sshCommand` overridden by `GIT_SSH_COMMAND`). Those are the only keys covered; in particular `remote.<name>.uploadpack` and `receivepack` cannot be overridden from the command line, so the harness never runs `ls-remote`, `fetch` or `push` against a workspace remote name. The remote-branch check never contacts a remote by name: it reads the harness-created bare repository at the path recorded when the sandbox was created. Bash commands are also collected while the agent's output streams (up to 5000), so the forbidden-command check still sees early commands when the in-memory transcript is truncated; if the list itself is incomplete the check fails rather than passes.
- **Redaction.** Every allowlisted credential value present in the environment is replaced by `[REDACTED]` (raw, JSON-escaped, URL-encoded and base64 forms) in the agent transcript before it reaches the checks or the judge prompt, and in the stored report and every console line, including errors. Other encodings (hex, split or transformed values) are not detected. The report lists allowlisted variable names only, never environment values.
- **Cost cap.** `--max-usd N` per suite, default $50 (`evals/limits.json`). Each in-flight run reserves `--run-usd` (default $5, also passed to `claude --max-budget-usd`) plus `--judge-usd` (default $0.50) when the eval has an active judged check. A run starts only when spend plus all in-flight reservations plus its own reservation fit under the cap, so under `--concurrency N` (default 4) the total never exceeds it. Judge-call cost counts in the eval's `costUsd` and in spend. A run whose cost is unknown (timeout, crash, failed judge call: no reported figure) is charged its full reservation and marked `costEstimated: true`, so failing runs still consume the cap. Evals that never start are `incomplete` (`pass: null`, neither pass nor fail).
- **Timeout.** `--timeout SEC` per run, default 900 (a scenario's `timeoutSec` can only lower it; `--timeout` above the `limits.json` value is an error). The run is started in its own process group; on timeout the group (the agent and its child processes) is killed and the run is recorded `timed_out`, which counts as a failure. A descendant that deliberately leaves the process group (for example with `setsid`) is not killed, but cannot delay the result by more than about a second. Check commands and the judge call run under the same group kill and timeout, without blocking other runs.

`outcome` per eval is `pass`, `fail`, `timed_out` or `incomplete`. The report carries `passed`, `failed` (fail plus timed_out), `incomplete`, `totalCostUsd` and `peakCommittedUsd` (highest spend plus reservations seen).

Limits and defaults are plain data in `evals/limits.json`; flags override them.

## Results

`evals/results/<model>-<timestamp>.json` (gitignored): per eval: `pass`, `verdict` (from deterministic checks only), `judgedScore` and `judgeModel` (judged checks only, `null` when none ran), `skill`, per-grader results (judged graders carry `judged: true`, and `refused: true` when the judge was refused), turns, cost. See exit codes below.

## Skill evals

One eval per skill, as plain files (no build step, no registration; the loader scans `evals/skills/`):

```text
evals/skills/<skill>/eval.json   task, skill, checks
evals/skills/<skill>/fixture/    starting workspace, committed on `main` in the sandbox
evals/skills/<skill>/rubric.md   optional rubric for judged checks
```

```bash
node evals/new.js <skill>                     # scaffold eval.json + fixture/ (skill must exist under packages/*/skills)
node evals/run.js --dry-run [--skill <skill>] # list evals; rejected ones are named with the problem (exit 2)
node evals/run.js --skill <skill> --model sonnet --judge-model opus --max-usd 1
```

`eval.json` fields: `skill`, `prompt` (plain language, the task as a user would ask it), `checks` (required); `id` (defaults to the directory name), `description`, `runtimes` (default `["claude"]`; the eval runs only under a listed runtime), `invocation` (`plain` default; `explicit` with a `command` such as `/ensemble:create-prd`, prefixed to the prompt on the with-skill arm; `explicit-both`, the same prefix on both arms, for a command that lives in a package both arms load), `sharedPackages` (package names loaded in both arms, Claude-only; see below), `sandboxPath` (fixture directories put first on the agent's PATH, never on the checks'), `remote` (`true` creates a bare `origin` for the sandbox), `branch` (checks out that branch, other than `main`, and with `remote` pushes it), `allowedTools`, `maxTurns`, `timeoutSec`, `repeats`, `bar`, `expectInvoked`. Unknown fields and unfilled `TODO:` placeholders are rejected. `repeats`, `bar` and `expectInvoked` act since PR 3 (see Arms and repeats). `runtimes` acts since PR 4: under `--runtime pi` an eval that does not list `pi` is skipped with a `SKIP` line, and legacy agent scenarios are Claude-only. No field is accepted-but-ignored any more.

A definition is rejected, and nothing runs for it, when it lacks a task, a `fixture/` directory, a skill or checks; names a skill with no `SKILL.md` under `packages/*/skills`; has only judged checks; or has a judged check with no rubric. Other evals still run.

Checks are the graders below. A `{ "type": "judge", "rubric": "..." }` check is judged: it needs a rubric (inline or `rubric.md`), is marked `judged` in results, and is reported as `judgedScore` apart from `verdict`. The judge model comes from `--judge-model` or `EVALS_JUDGE_MODEL` and must differ from `--model` (names are compared after normalising, so `sonnet` and `claude-sonnet-5-5` are the same model); without `--model` there is nothing to compare against, so the judged check is refused as well. A refused judged check names the conflict and the deterministic checks still decide the eval.

`evals/scenarios/` stays as legacy single-arm scenarios, not counted as skills. A skill eval whose id matches a legacy scenario id is rejected. Exit codes: 0 all pass, 1 an eval failed or timed out, 2 usage error or rejected definition (also under `--dry-run`), 3 `claude` missing, 4 the suite finished with incomplete evals. When several apply, 2 comes first (a rejected definition), then 1 over 4, and 4 over 0.

## Arms and repeats

A skill eval runs two arms on identical fresh workspaces: **with-skill** (`--plugin-dir packages/<pkg>`, the package as shipped, never a copy) and **baseline** (no plugin for the skill under test). Both get `--setting-sources project`. The prompt is the same plain text in both; `invocation: explicit` prefixes `command` on the with-skill arm only, `explicit-both` on both. `sharedPackages` lists packages loaded in both arms (each job's `pluginDirs`: baseline = the shared packages, with-skill = the shared packages then the skill's own); a shared package may not be the one that ships the skill (that would leak it into the baseline), and an eval that sets one, or `explicit-both`, must list only `claude` in `runtimes` (Pi loads one skill and has no package commands). The evaluated package hash then covers the shared packages too, so editing one invalidates cached and committed results. Each arm runs 5 times by default (`repeats` and `bar` in `limits.json`: 4 of 5 must pass for the with-skill arm to be reliable). Details, the startup-event findings and the Claude/Pi uplift distinction: `docs/guides/skills-eval.md`.

- `--repeats N` overrides the eval's `repeats`; `bar` in `eval.json` overrides the default bar, otherwise the default bar scales with `--repeats`. A bar above the repeats is a usage error (exit 2). The report states repeats, bar and where each came from.
- `--update-baselines`: replace a committed baseline even when the check says `regression` or `not-comparable`, or the model is `unknown` (without it those never overwrite the file).
- `--runtime claude|pi` (`claude` is the default). Any other runtime prints `unsupported --runtime "X": not supported in this release`, runs nothing and exits 2. Every result and the report record the runtime. Pi runs through `pi --print --mode json` (binary on `PATH` or `EVALS_PI_BIN`); its with-skill arm is `--no-skills --skill <skillDir>`, its baseline `--no-skills`, its uplift is labelled **skill-level**, and its cost is the reported `usage.cost.total` (else the per-run ceiling, flagged `costEstimated`). Details and the spike findings: the "Pi runtime" section of `docs/guides/skills-eval.md`.
- Uplift is labelled **package-level (skills share a package)** for Claude: the whole package is loaded, not only the skill.
- A baseline that has the skill loaded or invoked aborts that eval, naming the leak (exit 1, no baseline score; runs not yet started are skipped). A baseline that completed with no skill list (Claude: startup event; Pi: system prompt) aborts the same way as `baseline isolation unverifiable: no startup skill list`; a baseline that crashed or timed out before any init event is not counted toward the baseline score.
- A fixture containing `.claude/`, `.mcp.json`, `.git`, `.gitmodules`-style config or a symlink pointing outside it is rejected (the sandbox copy also skips them). Judged checks run on the with-skill arm only.
- Each result records `invoked` (from the transcript's `Skill` events) and the evaluated copy (package path, skill hash, whether the working tree differs from the committed copy, checked over the skill's package and every `sharedPackages` package, with changed files named by repo-relative path). `expectInvoked` is report-only.
- Results: a skill eval is one entry in `results` with `withSkill`/`baseline` counts, `reliable`, `uplift` and the per-run results under `runs` (graders and cost per run). Budget reservation is per in-flight run, so at most `--concurrency` runs are reserved at once.

## Results, baselines, report and coverage

- **Stored results.** Besides `results` (eval-level), each suite log has `records`: one schema-checked record per executed run with `evalId, skill, skillVersion, skillHash, evalVersion, runtime, model, arm, invocationMode, run, outcome (pass|fail|timed_out|incomplete), invoked, costUsd, durationMs, graders, judgeModel, replay`. `skillHash` is a content hash of the skill directory, `evalVersion` of `eval.json` + `rubric.md` + `fixture/` (`evals/lib/hash.js`: sorted, line endings normalised, no mtimes, symlinks never followed). A run that was `unverifiable` or `aborted` is stored as `incomplete` with `incompleteReason`: never a pass or fail. `results.readResult(file)` rejects a record with a missing field, naming file and field. Records and summaries are redacted and carry no home paths; the full log in `evals/results/` is redacted but may show workspace paths (gitignored).
- **Baseline summaries.** A finished eval (every planned run executed and verified) writes `evals/baselines/<runtime>/<skill>.json` for committing: `skill, skillVersion, skillHash, evalVersion, model, runtime, granularity (package for claude, skill for pi), repeats, bar, withSkill, baseline, reliable, uplift, recordedAt`. An incomplete or aborted eval writes nothing. `model` is the id the runtime reported (`unknown` when none, which is comparable to nothing) and Claude summaries add `packageHash` (the whole package). Before writing, the run prints a regression check against the committed file (`results.checkAgainstBaseline`: `no-baseline`, `not-comparable` when model, runtime, eval version or repeats differ (a changed skill or package hash is only a printed note), `regression` when the committed summary was reliable and the new one is not, else `ok`). The file is written only for `no-baseline` or `ok` with a known model, or with `--update-baselines`; a `regression` prints `REGRESSION` and exits 1 (the file is not overwritten unless `--update-baselines`), a `not-comparable` result leaves the file and the exit code alone. Exit 2 (rejected definition, unstorable result) outranks 1. A corrupt committed file is an error. `EVALS_BASELINES_DIR` overrides the directory; when only `EVALS_RESULTS_DIR` is set (tests) baselines go beside it, never into the repository.
- **Report.** The run prints a per-skill report: with-skill rate, baseline rate, uplift and the reliability verdict. Uplift is a number with no pass/fail; it is labelled `package-level (skills share a package)` for Claude (`package-level (with-skill adds <packages>)` when the eval has `sharedPackages`) and `skill-level` for Pi, and the two are never compared. An incomplete or aborted eval is marked and gets no score. `report.buildReportFromBaselines(dir)` builds the same report from the committed summaries.
- **Coverage.** `node evals/coverage.js [--json] [--strict]` (`npm run evals:coverage`) lists every shipped skill (source skills under `packages/*/skills`, not `full`/`pi`/`codex`/`opencode`) once as `evaluated` (a valid `evals/skills/<skill>/eval.json`), `exempt` (reason in `evals/exemptions.json`, a flat `{ "<skill>": "<reason>" }` map you edit) or `missing` (also printed as uncovered; a blank reason counts as missing). Stale or duplicate exemptions, an exemption for a skill that has an eval, and bad skill directories are errors (exit 2). Missing skills do not fail the command unless `--strict` (exit 1). Legacy scenarios are not skills.

## Cache, comparison and replay

- **Cache** (`lib/cache.js`). A finished run is reused, with no model call and no cost against `--max-usd`, when everything that can change its outcome is the same: skill hash (Claude: the whole package hash, since the package is loaded; Pi: the skill hash), eval version (hash of `eval.json`, `rubric.md` and the fixture), the requested `--model`, runtime, arm, invocation mode, repeat index, `maxTurns`, `allowedTools`, the effective timeout and per-run budget (`--timeout`, `--run-usd`, capped by `--max-usd`), and the judge model for the with-skill arm. Any change reruns the affected runs only. There is no age limit; `--refresh` ignores stored results and writes fresh ones. Entries live under `evals/cache/<runtime>/<sha256 of the key>.json` (git-ignored; `EVALS_CACHE_DIR` overrides; beside `EVALS_RESULTS_DIR` when only that is set). **Without `--model` nothing is reused or stored** (the default model can change silently), and the run says so. Reused runs are reported (`reusing stored result ...`, `cache: N run(s) reused, M executed, K stored`) and recorded with `cached: true` and cost 0.
  - Stored: only a completed `pass` or `fail` with a known model and a reported cost, and (baseline arm) verified isolation. Never an incomplete, timed-out, unverifiable, aborted, leak-flagged or `unknown`-model run, never any run of an eval whose baseline leaked, and (unless `--update-baselines`) none of an eval that regressed against its committed baseline.
  - Read back as untrusted: the key and inputs inside the entry must equal the requested ones, the record must pass `validateResult`, the baseline isolation evidence is checked again, sizes are capped, `storedAt` must be an ISO-8601 UTC timestamp and a model, eval version, judge model or eval id holding a control character makes the entry invalid, and terminal control characters in reused text are stripped before they are printed. Every console print of a value read from a store or log (cache entries, committed baselines, suite logs) goes through one `stripControl` helper; `--json` output is not changed. An unreadable, corrupt, oversize, symlinked, FIFO or invalid entry is a **miss** with a `WARNING cache entry <name> ignored` line (the run executes). A symlinked or non-directory cache root or runtime directory is a store problem: exit 2, nothing run. A fresh result that would have to replace a symlink, FIFO or oversize entry is not written (`CACHE NOT WRITTEN`, exit 2).
- **Comparison** (`node evals/compare.js [--results FILE] [--baselines DIR] [--skill NAME] [--json]`, `npm run evals:compare`). Read-only. Compares each skill eval in a results log (default: the newest `evals/results/*.json`) with `evals/baselines/<runtime>/<skill>.json` using `results.compareSummaries`, the same rule `run.js` applies. Like for like means same **runtime, model, eval version and repeats** (an `unknown` model is never comparable). Comparable: the change in with-skill rate and uplift is printed, and a committed-reliable eval that is no longer reliable prints `REGRESSION skill <s> eval <id>` and exits 1. A changed skill or package hash is a printed note, not a reason to refuse (the skill changing is what a regression check is for). Not comparable or no baseline: a `NOT COMPARABLE` / `NOTHING COMPARABLE` notice, no regression claimed, exit unchanged. Exit: `0` ok, `1` regression, `2` the log or a baseline cannot be read (symlink, FIFO, oversize, malformed; outranks 1), `4` an incomplete result, or nothing compared (never a silent pass).
- **Replay.** Every failing run in the report is listed under `failing runs` with a command that reruns exactly that run: `node evals/run.js --scenario '<eval>' --runtime '<rt>' --model '<requested model>' --arm '<arm>' --run-index '<n>' --repeats '<N>' --timeout '<s>' --run-usd '<usd>' --refresh` (plus `--judge-model`/`--judge-usd` when a judge was active). A failing run is a with-skill `fail` or `timed_out`, a baseline `timed_out`, unverifiable or leaked run (a baseline that merely scores low is a measurement, not a failure), or a failing legacy scenario (`--scenario '<id>' ...`). The same command is stored in each record (`replay.command`). Every value is validated and single-quoted; a value that is not plain (spaces, quotes, `$`, control characters) gives `replay: unavailable` instead of an unsafe command. No environment variable, credential or machine path is in it; run it from the repository root, with the same credentials in the environment. `--arm` and `--run-index` run exactly that one run, always fresh: no cache read or write, no baseline write, no regression check. Exit: 0 pass, 1 fail or timed out, 4 incomplete; a baseline arm run has no verdict of its own (pass and fail both exit 0).

## Pilot evals

Four evals cover the pilot skills (`evals/skills/<skill>/`, scaffolded with `node evals/new.js <skill>`). Their checks are deterministic and live in `evals/checks/pilot-checks.js` (a script the eval's `commandOutputMatches` checks run from the repository, not from the workspace; it reads the files the skill wrote, never follows a symlink and runs no workspace program). `evals/tests/pilot-evals.test.js` runs every check against stubs that write conforming and bad output. What each eval asserts, and its known limits: the "Pilot evals" section of `docs/guides/skills-eval.md`.

| Eval | Runtimes | Task |
|---|---|---|
| `ensemble-create-prd` | claude, pi | `/ensemble:create-prd` from a product description, `--foreman` |
| `ensemble-refine-prd` | claude, pi | `/ensemble:refine-prd` on a seeded PRD with open markers, `--foreman` |
| `ensemble-create-trd` | claude | `/ensemble:create-trd` from a seeded locked PRD, `--foreman`. Claude only: on Pi its Step 1.2 resolves `trd-cli` through the `tool-path-resolution` tiers, which fail in a sandbox unless an ensemble-pi bundle is installed, so the with-skill Pi arm would halt (a spurious negative uplift). Re-enable `pi` after a Pi trial on a host with the bundle shows it runs |
| `pr-merge-trace` | claude | `/ensemble:pr-merge` against a stub `gh` in a sandbox with a bare origin. **Not skill-attributable until a trial shows otherwise** (see below) |

The fixtures carry a minimal `docs/standards/constitution.md` (the Constitution Gate halts without one); the legacy `scenarios/create-trd` fixture has the same file. Pilot run size: Claude 4 evals, Pi 2 (`ensemble-create-prd`, `ensemble-refine-prd`; neither skill resolves a CLI by path, a search of their skill directories finds no `*-cli` reference).

`pr-merge-trace` caveat: the baseline arm loads `packages/git` only, so `toolchain-cli` cannot be resolved at step 1.1 of `ensemble-pr-merge` and the baseline certainly halts before any `gh` call; whether the with-skill arm resolves it depends on `${CLAUDE_PLUGIN_ROOT}` substitution, which is unproven. Its uplift may reflect the package being present, not the skill, so it is not skill-attributable, and the pilot does not count, until a maintainer-run trial (real run, one repeat) shows the with-skill arm gets past step 1.1. The report labels it `package-level (with-skill adds development)`: any eval with `sharedPackages` names the package its with-skill arm adds (stored in a committed baseline as `withSkillAdds`).

`gh-no-merge` fails on `gh pr merge` and on an `api graphql` call carrying a `mergePullRequest` or `enablePullRequestAutoMerge` mutation (any case); the PR counts as read only when a call's first words are `pr view`. The stub logs one line per call (newlines inside an argument are folded to spaces).

## Add a scenario (legacy)

1. `evals/scenarios/<id>/scenario.json`: `type` (`agent`|`cli`), `prompt`, `plugins`, `allowedTools`, `permissionMode`, `maxTurns`, `timeoutSec`, optional `remote: true` (bare `origin`), and `graders`. `{{repo}}` expands to the repo root.
2. `evals/scenarios/<id>/fixture/`: files copied into the sandbox and committed on `main`.
3. Graders live in `evals/lib/graders.js` (`trdParses`, `fileExists`, `fileMatches`, `testsPass`, `commandOutputMatches`, `noProtectedBranchCommit`, `remoteBranchUnchanged`, `noForbiddenCommand`, `judge`). Add new ones as plain functions with a test (all are deterministic except `judge`, which calls a model).

Tests: `npx jest evals` (uses a stub `claude`; no model calls).
